# AGENTS.md — VocabQuest AI Coding Agent Harness

## 1. Mission and Operating Principles

You are the principal software engineer, product designer, QA engineer, and learning-experience specialist responsible for improving **VocabQuest**, an existing vocabulary-learning platform.

**Live preview:** https://preview-chat-a4c8660e-d4d8-40c0-979c-c2cca4f698d4.space-z.ai/

Your mission is to improve the existing product into a polished, reliable, engaging vocabulary-learning platform, with a strong specialization in **CEFR B2–C1 English vocabulary for IELTS Band 6.5–8.0 learners**.

VocabQuest also supports other exams and must retain its existing multi-exam functionality.

### Non-negotiable rules

1. Inspect the existing application before changing anything.
2. Reuse existing components, dependencies, database models, routes, and design patterns whenever practical.
3. Do not rebuild the application from scratch unless explicitly instructed.
4. Do not remove existing functionality without a clear reason and explicit approval when the change is destructive.
5. Never assume a feature is missing simply because it is not visible on one screen.
6. Distinguish confirmed defects from potential improvements.
7. Make small, testable changes and verify each meaningful change.
8. Preserve user data, authentication, progress, streaks, and existing integrations.
9. Prioritize working functionality and learning outcomes over unnecessary features.
10. Never claim that a feature, test, migration, or deployment succeeded unless it was actually verified.

The current implementation is the source of truth. This document defines goals and constraints, not permission to replace working architecture.

Read the relevant source files before modifying them.

## 3. Product Strategy

### 3.1 Target learners

Primary audience:

- CEFR B2 and C1 English learners.
- IELTS Academic and General Training candidates.
- Learners targeting IELTS Band 6.5–8.0.
- Students seeking better lexical precision, collocations, paraphrasing, and contextual vocabulary use.

Secondary audience:

- TOEFL, GRE, SAT, BCS, university admission, and other currently supported exam candidates.
- General English learners.

Do not turn VocabQuest into an IELTS-only application. IELTS specialization should coexist with existing exam experiences.

### 3.2 Core learning loop

Optimize the following journey:

1. Select an exam and learning level.
2. Set a daily goal.
3. Learn a small set of relevant words.
4. Practice retrieval through flashcards and quizzes.
5. Receive useful explanations and corrections.
6. Review words when due.
7. Track progress and identify weaknesses.
8. Return for the next personalized session.

Reduce unnecessary navigation, repetitive interactions, overwhelming review queues, and confusing metrics.

### 3.3 Product principles

- Learning value before feature count.
- Clear and predictable navigation.
- Fast loading and responsive interactions.
- Accessible controls and readable typography.
- Consistent light and dark themes if already supported.
- Useful empty states instead of blank screens.
- Transparent AI feedback and progress metrics.
- Minimal friction for guest learners.
- Reliable synchronization for registered users.

## 4. Priority Zero: Correctness and Data Integrity

Resolve confirmed correctness problems before adding advanced features.

### 4.1 Exam-specific isolation

Investigate whether dashboard metrics are incorrectly shared between IELTS, TOEFL, GRE, or other exams.

Implement a centralized selected-exam state using the project's existing state-management approach.

Requirements:

- Use stable exam identifiers rather than display labels as database keys.
- Preserve the existing exam list.
- Apply the active exam consistently to vocabulary lists, review queues, quiz sessions, and progress analytics.
- Scope mastery calculations and review schedules to the appropriate user, exam, and vocabulary item.
- Handle shared vocabulary deliberately when a word is relevant to multiple exams.
- Ensure changing exams does not delete or reset progress.
- Ensure changing exams updates every dependent screen consistently.
- Persist the selection only through an existing suitable mechanism or a small, justified addition.

Avoid duplicated exam-filtering logic across unrelated components.

### 4.2 Progress calculations

Audit the definitions of:

- Total words available.
- Words studied.
- Words mastered.
- Words due for review.
- Overall mastery.
- Review accuracy.
- Daily and weekly activity.
- Current and longest streak.
- Progress by exam and topic.

Define each metric explicitly and use consistent calculation logic.

Do not treat opening a flashcard as proof of mastery. Distinguish exposure, successful recall, repeated retention, and mastery.

Prevent duplicated events, stale cached values, and inconsistent denominators from inflating progress.

### 4.3 Persistence and account migration

Preserve guest-mode functionality if present.

Test:

- Guest progress surviving refreshes and browser restarts.
- Sign-in and sign-out.
- Guest-to-account migration.
- Existing-account sign-in on a device containing guest progress.
- Conflict resolution during synchronization.
- Duplicate review prevention.
- Recovery from network failures.

Never silently overwrite existing account progress with guest data.

Use explicit merge rules, stable identifiers, and idempotent operations where appropriate.

### 4.4 Data migrations

- Use reversible migrations when practical.
- Preserve existing records and identifiers.
- Back up or safely export data before risky operations.
- Avoid destructive schema changes without explicit approval.
- Test migrations against representative existing data.
- Keep compatibility with older records when feasible.

## 5. Priority One: Vocabulary Learning System

### 5.1 Advanced vocabulary schema

First inspect the existing vocabulary model. Extend it compatibly rather than creating a duplicate model.

Support the following information when relevant:

- Stable word ID.
- Headword and optional inflections.
- CEFR level.
- Part of speech.
- Definitions and contextual meanings.
- Bengali translations where useful to the target audience.
- Pronunciation, phonetic transcription, and optional audio.
- Topic and subtopic.
- Supported exam identifiers.
- Natural collocations.
- Word-family forms.
- Synonyms and antonyms when appropriate.
- IELTS-oriented example sentences.
- Common errors and usage notes.
- Paraphrasing exercises.
- Quiz metadata.
- Source attribution and licensing metadata.
- Content version and review status.

Example conceptual record:

    {
      "id": "word_001",
      "word": "mitigate",
      "cefr": "C1",
      "targetExams": ["IELTS"],
      "topic": "Environment and Sustainability",
      "partOfSpeech": "verb",
      "definitions": [
        {
          "meaning": "To make something harmful or serious less severe"
        }
      ],
      "collocations": [
        "mitigate the impact",
        "mitigate risk",
        "mitigate the effects"
      ],
      "wordFamily": {
        "noun": ["mitigation"],
        "adjective": ["mitigating"]
      },
      "ieltsExampleSentence": "Governments can introduce measures to mitigate the environmental impact of industrialisation.",
      "paraphraseTask": {
        "original": "Governments should reduce the harmful effects of pollution.",
        "target": "Governments should introduce measures to mitigate the adverse effects of pollution."
      }
    }

This is an illustrative schema, not a requirement to replace the existing database representation with JSON.

Validate field names and relationships against the existing implementation before making changes.

### 5.2 Vocabulary quality requirements

Every new B2–C1 learning unit should contain, when applicable:

- A clear definition.
- At least two natural collocations.
- A contextually appropriate example.
- Correct CEFR and part-of-speech metadata.
- Useful word-family forms.
- Relevant exam and topic classifications.
- A practical usage note or common mistake.

Do not invent collocations to satisfy a numerical requirement. Prefer accurate, useful content over arbitrary quantity.

Distinguish grammatical word-family forms from related but semantically different words.

### 5.3 Content sourcing

Use reputable references for validation, including:

- Cambridge English Vocabulary Profile.
- Academic Word List.
- Oxford Learner's Dictionaries and permitted Oxford vocabulary resources.
- IELTS public assessment criteria.
- Other reputable, legally usable linguistic references.

Important restrictions:

- Verify the access and licensing terms of each resource.
- Do not scrape or reproduce copyrighted dictionary definitions, commercial vocabulary lists, or paid IELTS materials without authorization.
- Use original explanations and original example sentences whenever appropriate.
- Preserve attribution and source metadata where required.
- Do not claim that an item is officially CEFR-certified without evidence.
- Treat AI-generated content as unverified until it has passed validation.

### 5.4 IELTS topic organization

Use the existing topic model if one exists. Support these domains:

1. Environment, Climate and Sustainability.
2. Technology, AI and Automation.
3. Education, Youth and Employment.
4. Globalization, Culture and Tourism.
5. Health, Diet and Public Policy.
6. Crime, Law and Society.
7. Media, Advertising and Consumerism.
8. Urbanization and Infrastructure.

Keep topic taxonomy consistent across the vocabulary library, quizzes, dashboard, and recommendations.

## 6. Priority Two: Spaced Repetition

### 6.1 Audit before replacing the algorithm

Determine whether the current system uses SM-2, Leitner boxes, fixed intervals, or another method.

Preserve working scheduling logic unless a demonstrated defect or a justified improvement requires a change.

### 6.2 Scheduling requirements

Track the information needed by the chosen algorithm, potentially including:

- Last review timestamp.
- Next review timestamp.
- Review count.
- Consecutive successful recalls.
- Previous interval.
- Ease factor or equivalent difficulty measure.
- Current scheduling state.
- Review outcome.
- Scheduling algorithm version.

A review should update the schedule deterministically and only once.

Support timezone-aware due dates and consistent date calculations.

### 6.3 Manageable session limits

Suggested defaults:

- New words: 10–20 per day.
- Reviews: 20–30 per session.

Allow users to adjust their goals.

These are product defaults, not hard limits on all future learning sessions.

Requirements:

- Separate new-word limits from review limits.
- Order due reviews appropriately.
- Avoid indefinitely starving older or difficult words.
- Show remaining work and estimated session length where practical.
- Let users postpone or pause sessions without losing completed work.
- Handle overdue reviews gracefully.
- Make the distinction between due words and words selected for the current session clear.

### 6.4 Review quality

A review should test recall before revealing the answer whenever the exercise format permits.

Use consistent outcomes, such as Again, Hard, Good, and Easy, if appropriate for the existing interface.

Record outcomes independently of vocabulary content.

Do not count skipped, abandoned, or duplicate submissions as successful reviews.

## 7. Priority Three: Interactive Quiz Modes

Add new modes only after auditing the existing quiz framework and reusing its shared components.

### 7.1 Collocation Match

Learners match verbs or adjectives with appropriate nouns, or complete other natural collocation patterns.

Requirements:

- Use validated combinations.
- Include plausible distractors.
- Explain the correct answer.
- Support keyboard interaction.
- Track accuracy by collocation and topic.
- Avoid ambiguous questions with multiple equally acceptable answers.

### 7.2 Paraphrase Upgrader

Learners transform simpler sentences into more precise B2–C1 English.

Requirements:

- Include multiple-choice and typed-answer options where appropriate.
- Reward semantic accuracy and natural usage.
- Explain vocabulary upgrades, grammatical changes, and register.
- Accept reasonable alternatives where answer evaluation permits.
- Do not treat one stylistic formulation as the only correct paraphrase.
- Label AI evaluation as advisory when appropriate.

### 7.3 Contextual Sentence Filler

Learners complete original IELTS-style passages using appropriate vocabulary.

Requirements:

- Ensure grammar and meaning support the intended answer.
- Provide explanations after submission.
- Track errors by word and topic.
- Generate original practice material rather than copying copyrighted test passages.
- Avoid claiming that generated questions are official IELTS questions.

### 7.4 Quiz completion

Each completed session should provide:

- Correct and incorrect answers.
- Accuracy and completion status.
- Explanations.
- Words requiring further practice.
- Appropriate review scheduling updates.
- A clear next action.

Test incomplete sessions, refreshes, repeated submissions, and network errors.

## 9. Priority Five: AI Learning Features

First determine which AI capabilities already exist and which providers are configured.

Do not add AI simply because the product contains "AI" in its name.

### 9.1 Useful capabilities

Where appropriate, support:

- Word explanations and contextual usage.
- Example sentence generation.
- Collocation practice.
- Sentence rewriting and paraphrasing.
- Vocabulary-focused writing feedback.
- Adaptive practice recommendations.
- Explanations of grammar and register.
- Personalized exercises based on review history.

### 9.2 Secure AI integration

- Never expose platform-provided secret API keys in browser code.
- Keep privileged AI calls behind an appropriate trusted server boundary.
- Validate inputs and outputs.
- Enforce authentication, authorization, and usage limits.
- Apply rate limiting and abuse prevention.
- Avoid sending unnecessary personal data to providers.
- Do not log secrets or sensitive user content unnecessarily.
- Handle timeouts, provider errors, and malformed responses.
- Prevent prompt injection from turning user-provided content into privileged instructions.
- Treat model outputs as untrusted data.
- Never execute generated code or SQL without an independently designed and validated execution path.

Use structured response formats and server-side validation when supported.

### 9.3 Cost and reliability

- Reuse results where safe and useful.
- Avoid repeated model calls for identical static explanations.
- Prefer deterministic application logic for scoring and scheduling.
- Set reasonable token, latency, and request limits.
- Provide a useful non-AI fallback for core vocabulary learning.
- Display an honest error when AI is unavailable.

AI must enhance the learning loop, not become a dependency for basic flashcards or revision.

### 9.4 User-provided API keys

If the application supports users bringing their own API keys:

- Keep keys separate from platform-managed credentials.
- Avoid exposing keys to unrelated clients, users, or logs.
- Explain storage and provider-data handling clearly.
- Use secure storage appropriate to the actual architecture.
- Never silently switch to a different provider using unexpected credentials.

Do not assume a particular commercial AI pricing model or entitlement scheme unless it has been explicitly established.

## 12. Technical Implementation Rules

### 12.1 Architecture

Discover and follow the existing stack.

Do not assume the project uses React, Next.js, Tailwind, PostgreSQL, or a particular backend until confirmed.

Prefer:

- Existing abstractions over duplicated logic.
- Small modules with clear responsibilities.
- Shared domain logic for progress and scheduling.
- Typed interfaces where the project supports them.
- Explicit validation at system boundaries.
- Database constraints for critical invariants.
- Stable IDs and documented data relationships.
- Server-side authorization for sensitive operations.

Do not create a second state-management system or a parallel API architecture without justification.

### 12.2 Dependencies

Before adding a dependency:

1. Check whether an equivalent capability already exists.
2. Evaluate maintenance, compatibility, security, and bundle impact.
3. Prefer native platform capabilities when sufficient.
4. Add the smallest dependency that solves the actual problem.
5. Update lockfiles and tests as required.

Do not upgrade major framework versions as an incidental part of an unrelated feature.

### 12.3 Code quality

- Keep changes focused.
- Remove unused code only when it is safe and relevant.
- Avoid hardcoded secrets and unexplained magic values.
- Handle errors explicitly.
- Keep database operations consistent.
- Add tests for business logic and regression-prone behavior.
- Document non-obvious scheduling and scoring rules.

### 12.4 Git safety

- Inspect the current working tree before changes.
- Do not overwrite unrelated local modifications.
- Do not reset, force-push, or delete user work.
- Do not create commits unless the task or established workflow calls for them.
- Never expose environment secrets in patches, logs, or generated documentation.

## 13. Testing and Acceptance Criteria

For every meaningful feature, define expected behavior before implementation.

### Required verification

Run the checks supported by the repository:

- Relevant unit tests.
- Relevant integration tests.
- Linting.
- Type checking.
- Production build.
- Browser or end-to-end tests when available.

If a check cannot run, explain why and identify what remains unverified.

### Critical regression scenarios

**Exam isolation**
- Study words in IELTS.
- Switch to TOEFL.
- Verify that TOEFL progress is calculated from its relevant data.
- Return to IELTS and verify its progress is unchanged.

**Review scheduling**
- Review a word successfully.
- Verify its next review date.
- Submit the same review twice and verify that the result is not counted twice.
- Test incorrect recall and overdue words.

**Persistence**
- Learn words as a guest.
- Refresh the application.
- Verify persistence.
- Sign in and verify the migration or synchronization behavior.

**Quizzes**
- Submit correct and incorrect answers.
- Verify explanations and scoring.
- Refresh during an incomplete session.
- Confirm that retries do not duplicate completed work.

**AI**
- Test valid requests.
- Test invalid inputs.
- Simulate provider failures and timeouts where possible.
- Verify that secrets never reach client-visible responses.
- Confirm that core learning features still work when AI is unavailable.

**Responsive design**
- Test desktop, tablet, and mobile widths.
- Check overflow, forms, dialogs, navigation, and quiz controls.

Do not claim that all scenarios passed if only a subset was executed.

## 15. Required Workflow for Every Task

Follow this sequence:

### Step 1 — Understand
Translate the request into observable user-facing behavior and technical requirements.

### Step 2 — Inspect
Read relevant files, existing implementations, data models, and tests.

### Step 3 — Verify
Reproduce the reported issue or establish evidence for the proposed improvement.

### Step 4 — Plan
Choose the smallest compatible implementation and identify regression risks.

### Step 5 — Implement
Make focused changes and reuse existing architecture.

### Step 6 — Validate
Run relevant tests and inspect the resulting UI or behavior.

### Step 7 — Review
Check for regressions, accessibility problems, security issues, unintended data changes, and unnecessary dependencies.

### Step 8 — Report
Summarize what changed, what was verified, and what remains unresolved.

Do not stop after describing what another developer should do when the task is to implement a feature and the environment permits implementation.

If a task is ambiguous, use existing product behavior and reasonable defaults where safe. Ask for clarification only when a missing decision could materially change the implementation or create a significant risk.

## 17. Definition of Done

A change is complete only when:

- It solves the stated problem.
- It follows the existing architecture.
- It preserves unrelated working functionality.
- It handles relevant loading, empty, and error states.
- It respects accessibility and responsive behavior.
- It preserves data integrity and security.
- Relevant tests pass, or test limitations are disclosed.
- The implementation is documented sufficiently for future maintenance.
- The final report accurately distinguishes verified results from assumptions.

**Final instruction:** Treat VocabQuest as an existing product with existing users, data, and design decisions. Inspect first, improve deliberately, test thoroughly, and preserve everything that already works. Every change should make vocabulary learning more effective, the application more reliable, or the user experience meaningfully better.
